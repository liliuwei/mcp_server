## 订单查询方式实测（以 MG3812 隐藏单为例）

| 查询方式 | 结果 |
|---|---|
| `ids=MG3812`（订单号当 ID）| 0 笔 |
| `ids=<真实ID>`（不加 hidden_order）| **0 笔**（隐藏单被过滤）|
| `ids=<真实ID>&hidden_order=true` | ✅ 1 笔 |
| `name=MG3812` | 0 笔（隐藏单被过滤）|
| `name=MG3812&hidden_order=true` | ✅ 1 笔 |
| `search_content=MG3812` | 0 笔 |
| `search_content=MG3812&hidden_order=true` | ✅ 1 笔 |
| `orders/{ID}.json`（详情端点）| ✗ **接口不存在**（返回 `{"errors":"method not allowed"}`）|
| `name=MG1910`（正常单）| ✅ 1 笔 |

结论：
1. **没有订单详情专用端点**，一切订单查询都只能走 `orders.json` + 条件参数。
2. **`ids` 只认数字订单 ID，不认订单号**（`MG3812` 传 ids 直接 0 笔）；订单号只能通过 `name`（或 `search_content`）传。
3. **隐藏单必须带 `hidden_order=true` 才可见**——无论用 ids 还是 name 都如此。这正是已实现的兜底所解决的问题。
4. 因此 `get_order(order_id="MG3812")` 必然失败：既不是数字 ID，且未带 hidden_order。
5. 若要支持，方案：`order_id` 含非数字字符 → 自动改用 `name` 查询；纯数字 → 用 `ids`。配合已有兜底即可。
