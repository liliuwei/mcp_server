## 订单「签收状态」调研结论：SHOPLINE 未回传，拿不到

### 背景
用户问订单查询接口能否看到签收状态，并提供了官方接口
`GET /orders/{order_id}/fulfillments.json`（获取订单下的所有发货单）。

### 实测（订单 MG32606）
- 订单 id `21077469157936154907189922`，**隐藏订单**（需 `hidden_order=true` 才查得到）
- status=open，financial=paid，fulfillment_status=fulfilled，fulfillment_status_v2=shipped
- 发货单：id `22077469475352693118479922`，status=`success`
- 物流：UPS，单号 `1Z256R4F4217299871`，tracking_url `https://www.ups.com`（通用首页，非深链）
- 发货时间 2026-10-16 00:36:04，updated_at 与 created_at **相同**（无轨迹更新）
- **`shipment_status` = null**

### 专用接口验证
- `orders/{order_id}/fulfillments.json` → **HTTP 200，接口存在可用**
- 返回字段与订单对象里的 `fulfillments[]` **完全一致**（另多出已废弃的 `tracking_numbers`/`tracking_urls`）
- `shipment_status` 仍为 null
- 其他路径均 404：`orders/{id}/fulfillments`、`fulfillments.json?order_id=`、`orders/{id}/fulfillments/list.json`
- `orders/{id}.json` → 405 method not allowed（详情端点确实不存在）

### 批量抽样（决定性证据）
最近 100 笔订单（created_at_min=2026-08-01，hidden_order=true）：
- 含发货单订单 100 笔，**发货单总数 107 条**
- **`shipment_status` 分布：`{'None': 107}` —— 全部为 null，没有一条有值**

### 结论
1. **不是接口问题，是上游没数据**：SHOPLINE 这个店铺完全没有回传物流轨迹，`shipment_status` 恒为 null。
2. 换成专用发货单接口**没有任何收益**（字段相同、值也相同）。
3. 因此**不必**把该接口加进白名单或新增 `get_order_fulfillments` 工具——加了也是 null。
4. 想拿签收状态只能走**第三方轨迹**：用 `tracking_info_list` 里的 company+number 调 UPS/FedEx 官方 API 或 17TRACK/TrackingMore 等。
   注意 `tracking_url` 只有 `https://www.ups.com` 这种通用首页，无法直接定位包裹。
5. 也可排查 SHOPLINE 后台是否需绑定承运商/开启轨迹订阅，但当前证据表明未生效。

### 字段坑（后续做状态判断时注意）
`shipment_status` 官方枚举：`out_for_delivery` / `delivered` / `picked_up` / **`faliure`**（官方拼写错误，非 failure）。
废弃字段：`tracking_numbers`、`tracking_urls`、`tracking_company`、`tracking_number`、`tracking_url`（v20250301/v20250601 起），取数以 `tracking_info_list` 为准。

### 其他发现
- MG32606 同样是**隐藏订单**，再次印证按订单号检索必须带 `hidden_order=true`（本项目已内置兜底）。

### 补充实测：MG3812（用户要求单独测）
- 订单 id `21071356717618744607449368`，status=open / paid / fulfilled / shipped
- 下单 2025-08-20，订单 updated_at 2025-09-20
- 发货单 id `22071595234890403515299368`，status=`success`，**shipment_status=None**
- FedEx `392884419893`，created_at = updated_at = 2025-09-05T18:42:43（从未更新）
- `tracking_url` = **null**（MG32606 的 UPS 是 `https://www.ups.com` 通用首页）→ 该字段不可靠
- `return_info` = NO_RETURN
- 专用接口 `orders/{id}/fulfillments.json` 返回同样结果，`shipment_status` 仍为 null
- 结论与批量抽样一致：**上游无轨迹数据，换接口无效**。

## 订单相关接口全量实测（mileseeygolf / v20260901）

### ✅ 可用接口
| 接口 | 返回 | 关键内容 |
|---|---|---|
| `orders.json` | `orders[]`（**92 字段/笔**）| 订单主体，已内嵌大部分关联数据 |
| `orders/{id}/fulfillments.json` | `fulfillments[]` | 发货单；**字段与 order.fulfillments 完全重复** |
| `orders/{id}/transactions.json` | `transactions[]` | id/kind(sale)/status/amount/currency/gateway/**payment_details(卡号掩码、bin、brand)** |
| `orders/{id}/refunds.json` | `refunds[]` | refund_line_items/transactions/order_adjustments/note |

| `orders/{id}/metafields.json` | `metafields`（常为 null）| 自定义字段 |
| `orders/count.json` | `{count}` | **支持 status / financial_status 过滤**（总 31280、open 316、cancelled 156、refunded 990）|
| `fulfillment_orders/fulfillment_orders_search.json` | `fulfillment_orders[]` | 履约单（16 字段）|

### ❌ 不存在（404）或不可用
`orders/{id}.json`(405)、`orders/{id}/returns|return|events|timeline|history|logs|shipments|shipping_lines|payment|discounts|notes|disputes|chargebacks|fulfillment_orders|customer|payment_details.json` 全部 404；
`returns.json` / `return_orders.json` / `draft_orders.json` / 各集合接口带 `order_id` 过滤均 404。
`orders/{id}/cancel.json` 405（需 POST）。

### 订单对象已内嵌（无需额外调用）
`customer(10)`、`line_items(33/项)`、`shipping_address(21)`、`billing_address(15)`、`fulfillments`、`locations`、`payment_details`、`shipping_lines`、`tax_lines`、`discount_codes`、`discount_applications`、**`refunds`（含 note/transactions，已足够）**、`return_info`、`note_attributes`、`client_details`。

### ⚠️ 发现的 3 个问题
1. **`fulfillment_status` 枚举我们写错了**：官方是 `unshipped` / `partial` / `shipped`；传 `unfulfilled` / `fulfilled` → **HTTP 500 `fulfillment status value is illegal`**。三个文件的工具描述都需修正。
2. **`list_fulfillment_orders` 的 `order_id` 过滤不生效**：实测传 `order_id` / `order_ids` / `order_ids[]` / `orderId` 均被忽略，返回该 location 下的全部履约单（3 条 3 个不同订单）。该参数是无效的。
3. `orders.json?ids=` 对**隐藏单**必须同时带 `hidden_order=true`，否则 0 笔（MG32606 实测）。
4. `status` 枚举：`open` / `cancelled` / `any` 有效，非法值 → 500 `status value is illegal`。
5. 文档称 `fulfillment_status` 默认 `unshipped`，但实测不传也能查到已发货订单——默认值未生效。
6. `orders/count.json` 的 `hidden_order` 过滤**不生效**（false/true 均 31280）。

### 获取订单全部数据的推荐调用序列
1. `orders.json?name={订单号}&hidden_order=true` → 主体（含客户/商品/地址/发货/支付/退款）
2. `orders/{id}/transactions.json` → 支付交易明细（卡号掩码等）
3. `orders/{id}/refunds.json` → 有退款时取明细
4. `orders/{id}/risks.json` → 风控评分
5. `orders/{id}/metafields.json` → 自定义字段
6. （可选）`orders/{id}/fulfillments.json` → 与内嵌重复，可省

## content.text 改为中文键值对（shopline_mcp.php → v2.3.0；shopline_mcp_v2.php → v2.1.0）

### 需求
`tools/call` 的 `content[0].text` 从「摘要 + JSON」改为**中文键值对描述**，方便大模型理解；`structuredContent` 保持原始 JSON 不变。

### 实现（两文件各新增约 480 行渲染器）
| 函数 | 作用 |
|---|---|
| `fieldLabels()` | 英文字段名 → 中文标签字典（约 230 条，覆盖订单/客户/地址/商品/库存/履约/物流/支付/风控） |
| `fieldLabel($key, $parent)` | 取标签；支持**按父级消歧**（`name` 在 orders→订单号、line_items→商品名称、locations→地点名称）；`*_set` 自动复用基字段 + "(含币种)" |
| `enumLabel($key, $value)` | 枚举翻译：status/financial_status/fulfillment_status(_v2)/kind/recommendation/return_status/shipment_status/gender/pay_status |
| `scalarText($key, $value)` | null→"空"、空串→"空"、布尔→"是/否"、枚举→`原值（中文）` |
| `renderChinese($data, $depth, $parent)` | 递归渲染；对象→缩进 `标签：值`；数组→`标签（共 N 项）：` + `第 N 项：` |

### 优化点
- **`*_set` 金额对象压缩成一行**（`商品小计(含币种)：USD 399.00`），避免 4 层重复嵌套 —— 单笔订单文本从 10893 → 8246 字符。
- `formatResult()` 改用 `renderChinese()` 生成 text，截断逻辑保留；`structuredContent` 逻辑不变。

### 实测
- `get_order` / `get_product` / `get_customer` / `list_fulfillment_orders` 的 text **无残留英文字段**（仅保留 ID/SKU/SPU/ASID 等专有名词）
- 单笔订单约 368 行 / 8246 字符
- `structuredContent` 仍为 `{orders:...}` / `{product:...}` / `{customer:...}`（含 `_page_info`）
- `php -l` 两文件无语法错误
- 注意：文本变长（368 行/单笔），`list_orders` 大批量时更容易触顶 50000 字符截断

## 售后场景改造：隐藏单合并 + get_order 支持邮箱（shopline_mcp.php → 2.4.0；v2 → 2.2.0）

### 需求背景
用户用于**客户售后服务**，`get_order` 高频查客户订单；旧逻辑「非隐藏单为空才补查隐藏单」会漏掉「客户同时有非隐藏单和隐藏单」的情况。

### 参数变更
| 工具 | 变更 |
|---|---|
| `list_orders` | 删除 `hidden_order`、`sort_condition` |
| `get_order` | 删除 `hidden_order`；`order_id` 改可选；新增 `email`；`required: []`；运行时校验"至少传一个" |

### 查询策略（`ordersRequestWithHiddenFallback` 已删除，拆成两个函数）
- **`ordersRequestBoth($q)`**（列表用）：`hidden_order=false` + `hidden_order=true` 各查一次 → 按 id 去重 → `created_at` 倒序 → 截断到 limit；两边都失败才报错；带 `page_info` 时**不合并**、原样透传。
- **`ordersRequestSingle($q)`**（单笔用）：先非隐藏、空了再查隐藏（短路，省一次调用）。

### get_order 新逻辑
1. `order_id` 与 `email` 至少传一个，否则 `isError`
2. `order_id` 含 `@` → `isError` 引导改用 `email`
3. 有 `order_id` → 先按订单号/ID 查（短路）；命中直接返回全量详情
4. 未命中且无 email → 「未找到…」
5. 未命中且有 email → 回落邮箱查询，摘要前缀「未找到订单号 XXX；」
6. 邮箱 1 笔 → 全量详情；多笔 → **精简列表**；0 笔 → 「邮箱 XXX 下也没有订单」

### 输出形态
- `list_orders` → **精简视图**（`renderOrderBriefList()`，每笔约 10 行：订单号/下单时间/应付总额/支付状态/发货状态/客户/邮箱/商品/物流/是否隐藏）
- `get_order` 单笔 → 全量详情（368 行）
- 新增辅助：`formatResultText()`（自定义正文）、`briefEnum()`、`briefItems()`、`briefTracking()`

- 合并后按 `created_at` 截断，若非隐藏单更"新"，隐藏单可能被挤出 limit（如 limit=20 时全部是非隐藏）。**目标查询（邮箱/订单号）结果集小，不受影响**。
